Razorpay · webhook correctness

The order says pending.
Razorpay has the money.

Nothing in either system will ever notice. Raze is the layer that notices — it reads a merchant's database, builds their Razorpay integration, and keeps the two in agreement. The merchant connects a database and supplies keys. Their own code does not change by one character.

The failure is ordinary

No exotic edge case. The most common integration shape there is.

A shop creates a Razorpay order, opens Checkout, and marks the order paid when the customer's browser comes back and says the payment succeeded. That is what a first integration looks like — it's the path the quickstart shows, and it works every single time you test it.

It works because you never close the tab. A customer on a train does. The card is charged, Razorpay has the money, and the shop's order book still says pending. The order isn't shipped. The customer's money is gone.

Razorpay's answer is webhooks, and their documentation then hands the merchant four hard problems: verify an HMAC over the raw body, deduplicate on x-razorpay-event-id, tolerate events arriving out of order, and answer within five seconds. Most small merchants solve none of them.

This repository ships a shop with exactly this bug. Nothing in it is sabotaged. No flag breaks it, no failure is injected, and nothing about Razorpay is simulated — it creates real Test Mode orders against the real API. It's written the ordinary way, and the ordinary way loses money.

What we measured

Razorpay documents "exponential backoff over 24 hours" and never publishes the schedule. So we recorded it.

Sixteen deliveries. Fourteen doublings, ratio 2.00 from the fifth gap onward. The stopping rule is the 24-hour window, not an attempt count — doubling continues until the next step would fall outside it. Two runs a day apart agreed on the 11.4-hour step to within five seconds, a 0.01% divergence. This schedule is not merely unjittered; it is clocked.

Six findings, and the line of code each one forces

What we measuredWhat it forces
First retry at 0.23 seconds Answer 200 before processing. A synchronous handler is guaranteed a duplicate, not merely at risk of one.
Nothing after 22.76 hours Waiting is not a recovery strategy. Reconciliation is mandatory.
Sustained failure disables the endpoint — observed directly, reproduced twice Delivery never resumes without human action, and the merchant's own system never tells them. A deadline is the only signal left.
HTTP 400 is retried on the same curve as 500 Rejecting a malformed webhook with a 400 earns another ten copies. 4xx is not a stop signal.
No retry counter in the request — only the event id, signature and user agent A receiver cannot tell attempt 1 from attempt 11. Deduplication must be stateful on the receiver's side. The most product-relevant thing we found, and it is a negative result.
Razorpay's list endpoints lag by minutes — found live while building this Reconciliation that only enumerates is blind exactly where a fresh payment lives. Ask about each open order by name instead.

What we got wrong

Three published claims, later overturned by more data. Kept, because a research process that only reports its wins isn't one.

We claimed the second retry tier depended on time of day. Runs 2 and 3 differed — 8.6s against 5.9s — and each run's modes clustered tightly enough that noise seemed ruled out. Run 4 refuted it: its within-run spread was 1.63s, wider than the between-run gap the entire story rested on. The tight clustering was itself coincidence. The honest number is ~6–9s, with no time dependence.

We claimed one event id identifies one delivery stream. It doesn't — Razorpay assigns one id per event and fans it out to every subscribed endpoint. Our first analyser merged five independent streams into one nonsense sequence.

We claimed one endpoint measured a connection reset. It didn't. The host's edge converted a destroyed origin socket into a 502 before Razorpay ever saw it. The limitation was the instrument, not the finding.

Had we built the demo around "Razorpay retries in 200ms" as a universal claim, a refund-based demo would have sat there looking broken for six seconds. The sample, not the instrument, was the limitation — which is the argument for insisting on four runs.

What Raze does

Given a database URL and a Razorpay key pair, and nothing else.

01Reads the schema. Decides which table holds orders, which column carries the Razorpay id, which says whether an order is paid, which money column records what was owed, and which records what arrived.
02Verifies every claim against the live database before believing any of it. Columns must exist, money columns must be numeric, key values must actually look like Razorpay order ids. Anything that fails is dropped.
03Builds the Razorpay side. Generates the signing secret, registers the webhook, subscribes only to events this schema can record, then reads the registration back from Razorpay to confirm it.
04Backfills. Asks Razorpay what it already recorded and reports what the database never applied — a real number, before anything is touched.
05Watches on three independent timers: reconcile every 60s, ask about every open order by name every 20s, sweep deadlines every 30s.

The one judgement it will not guess

One money column records what was owed. Another records what arrived. A payment is applied only after it agrees with the first. Get them backwards and every payment verifies against a figure it wrote itself — worse than no checking at all, because it produces a system that is confidently wrong. Where a schema doesn't clearly distinguish them, Raze reports divergence and never repairs unattended.

Where the model sits, and where it does not

A model proposes which column is which. Deterministic code then checks every claim against the live database. A wrong answer cannot arm a wrong mapping — the worst it can do is fail a check and cost the merchant a question. There is also a model-free reader that produces the same claim from the schema alone and passes identical verification. Nothing in the decision path involves a model; one test empties PATH and runs every tool anyway.

What it refuses to write

Anyone can build something that marks orders paid. The question is what it does when it should not write.

Every rule fails toward escalation. And a repair is not reported as done until Raze has read the row back out of the merchant's own table — an exception not being thrown proves nothing, and a queue accepting a row proves a row exists, not that money landed where the merchant can see it.

Why this isn't a faster integration

Razorpay's own agentic integration makes integration fast: understand the app, generate the integration, get payments working.

Fast integration is not enough. The integration should be hardened against the failure patterns we have actually measured — and the merchant's code should not have to change to get them.

Two differences follow. Raze generates no code into the merchant's application: the shop in the repository has no webhook handler and has never heard of Raze. And every protection exists because of a specific number in the measurement, not because a style guide recommended it.

Run it yourself

The whole demo works on a laptop. No webhook, no public address, no deployment — reconciliation asks Razorpay what it recorded rather than waiting to be told.

1Start the shop. Tick “customer closes the tab after paying”, place an order, complete the payment.
2The shop shows pending, ₹0.00 received. Razorpay has the money. Nothing will ever fix this — wait as long as you like.
3Connect Raze: key id, key secret, database URL. It reads the schema, builds the webhook, and starts watching.
4Within about twenty seconds the order is paid, received equals billed — written by Raze, verified by reading the row back.
5Then dismiss a payment window without paying. That order stays pending forever. Raze does not invent a payment.

npm test runs twelve layers replaying the real captured deliveries. npm run chaos kills a worker mid-transaction, fails a handler's first two attempts at every event, mixes forged deliveries into the stream, drops every delivery, and terminates the database underneath — each payment still lands exactly once. A build-failing control test asserts that a correct integration produces zero findings, so the tooling cannot quietly start reporting problems that aren't there.
